## What's left (per `docs/TDD.md` and `roadmap-esports-wiki-ai.md`)

- **Remaining `docs/TDD.md` "Future Improvements"** not yet started, in the order discussed:
  - **Parent Document Retriever** — discussed and **recommended to skip/defer**: it shines when child chunks are tiny (sentence-level) and need a much larger parent for LLM context; this project's chunks are already 1000 chars/200 overlap (`ingestion/splitter.py`), a size that doesn't have that problem. Doing it "properly" would mean revisiting Stage 3 chunking strategy first, which is a bigger scope than the last three retriever-flag features.
  - **Conversation Memory** — brainstormed 2026-08-09, then explicitly stopped by the user (already implemented elsewhere, with Postgres/Redis, no need to repeat it here). Agreed direction if resumed: client-side history only (`AskRequest` gains a `history: list[{role, content}]` field; no server-side persistence, no SQL) — the question of whether history should also affect retrieval (vs. only the final answer-generation prompt) was raised but never answered before the session ended. **History-aware Retriever** depends on Conversation Memory and was never reached.
  - **Streaming Responses** (API-layer, `/ask` → `StreamingResponse`) — not brainstormed, still open if development resumes.
- **Automatic game routing** (inferring the `game` metadata filter from the question text) — TDD explicitly defers this to "future versions." Right now callers must build the retriever with an explicit `metadata_filter={"game": ...}` themselves.
- **Non-goals per TDD** (still true for "the first version"): no auth, no frontend, no agents, no LangGraph, no MCP, no SQL. `roadmap-esports-wiki-ai.md`'s Phase 5 (UI), Phase 7 (Agents), Phase 8 (LangGraph) are annotated as explicitly deferred beyond v1, not permanently excluded — same status as before, now written down in the roadmap itself.

## How to resume

1. Pick the next feature (Streaming Responses is the main open candidate — see above; Conversation Memory is deliberately parked, not abandoned for lack of a plan) and branch it directly off `master` — there's no longer a chain of unmerged branches to stack on.
2. To try the full pipeline for real, in order:
   ```bash
   docker compose -f docker/docker-compose.yml up -d
   uv run --env-file .env python -m scripts.run_crawler
   uv run --env-file .env python -m scripts.run_indexer
   uv run --env-file .env python -m scripts.run_retriever   # interactive
   uv run --env-file .env uvicorn app.api.main:app --reload     # then curl below
   ```
   Note: `run_indexer` re-runs ingestion/chunking/embeddings internally (it chains from `data/raw/` forward), so running just `run_indexer` alone is enough to exercise the whole pipeline up through Qdrant. Equivalently, `POST /reindex` does the same work via the API in the background.
3. To manually compare retrieval strategies once the server is up and the collection is populated:
   ```bash
   curl -X POST http://localhost:8000/ask -H "Content-Type: application/json" \
     -d '{"question": "Who is s1mple?", "game": "cs2"}'                                          # dense-only (default)
   curl -X POST http://localhost:8000/ask -H "Content-Type: application/json" \
     -d '{"question": "Who is s1mple?", "game": "cs2", "use_hybrid": true}'                       # + BM25 fusion
   curl -X POST http://localhost:8000/ask -H "Content-Type: application/json" \
     -d '{"question": "Who is s1mple?", "game": "cs2", "use_multi_query": true}'                  # + LLM query rephrasing
   curl -X POST http://localhost:8000/ask -H "Content-Type: application/json" \
     -d '{"question": "Who is s1mple?", "game": "cs2", "use_compression": true}'                  # + LLM relevance filter
   # all three combine freely:
   curl -X POST http://localhost:8000/ask -H "Content-Type: application/json" \
     -d '{"question": "Who is s1mple?", "game": "cs2", "use_hybrid": true, "use_multi_query": true, "use_compression": true}'
   ```
   `use_multi_query` and `use_compression` each add real extra LLM calls (latency/cost) — `use_compression` the most (up to one per retrieved document).

## What's next — AI Assistant roadmap (active scope)

Per `docs/roadmap-ai-assistant.md`, in order:

1. **Milestone 1 — Done (2026-08-11).** `rag/service.py` now has `RAGService.answer(question, game=None, *, use_hybrid=False, use_multi_query=False, use_compression=False)`, hiding Qdrant/retriever/chain construction behind one call. `api/routes.py`'s `/ask` handler only depends on `RAGService` now (no more direct `build_retriever`/`answer_question`/`COLLECTION_NAME` imports). `rag/chains.py` and `rag/retriever.py` are unchanged, just called from inside the service. Sync, not async — the roadmap's illustrative signature was `async def answer(...)`, but the whole codebase (crawler, ingestion, API routes) is sync, and there was nothing actually I/O-bound-and-awaitable to gain from async here; kept consistent with existing conventions instead. Verified: 97/97 tests pass (3 new for `RAGService`), ruff/black clean. Three existing tests that spied on `build_retriever` at the `api.routes` module (`test_ask_passes_use_hybrid/use_multi_query/use_compression_flag_to_build_retriever`) were updated to spy on `rag.service` instead, since that's where the call moved to — expected fallout from moving the construction into the service layer, not a behavior change.
2. **Milestone 2 — Done (2026-08-11).** `get_player`, `get_team`, `get_match` LangChain tools (`tools/{player,team,match}.py`), each a thin `@tool`-decorated adapter with an explicit Pydantic `args_schema`, bound via a factory function (`make_get_*_tool(service)`) to avoid a global service singleton. Each tool delegates to its own `services/*_service.py` (`PlayerService`, `TeamService`, `MatchService`), which in turn depends on `services/data_source.py`'s `MockEsportsDataSource` — a small class reading `data/fixtures/{players,teams,matches}.json` (no real company data; matches roadmap §6's data source options). Not-found lookups raise domain exceptions (`services/exceptions.py`: `PlayerNotFoundError`/`TeamNotFoundError`/`MatchNotFoundError`), which propagate through `tool.invoke()` uncaught for now — deliberately deferred, since tool-call error *handling* is roadmap §12 (Milestone 5+ scope), not this one. Fixture entities (`NAVI`/`s1mple`, `T1`/`Faker`, `Sentinels`/`TenZ`) were chosen to match teams already present in `config/pages.json` so future RAG+tools questions (e.g. "Tell me about s1mple and his current team") have consistent data on both sides. Verified: 116/116 tests pass (19 new, covering services and tools independently, per acceptance criteria), ruff/black clean, plus a manual end-to-end sanity check wiring the real `MockEsportsDataSource` through all three real services and tools.
2.5. **Milestone 2.5 — Done (2026-08-11).** `api/`, `rag/`, `tools/`, `services/` moved under a new top-level `app/` package (`app/api/`, `app/rag/`, `app/tools/`, `app/services/`), matching `docs/roadmap-ai-assistant.md` §23's target tree. Pure relocation: every `api.*`/`rag.*`/`tools.*`/`services.*` import became `app.api.*`/`app.rag.*`/`app.tools.*`/`app.services.*`, tests moved from `tests/{api,rag,tools,services}/` to `tests/app/{api,rag,tools,services}/`, `uvicorn api.main:app` became `uvicorn app.api.main:app`. `crawler/`, `ingestion/`, `scripts/`, `config/`, `data/` untouched. `app/agents/`/`app/workflows/` deliberately not created yet (no content until Milestones 5/6 — would otherwise be empty placeholder packages). Two bugs the plan hadn't anticipated, both fixed during execution: `services/data_source.py`'s `DEFAULT_FIXTURES_DIR` computed from `__file__` needed an extra `.parent` to account for the new nesting level; and `tests/api/test_routes.py` already had a local `app` (the FastAPI instance) that collided with a naive `import app.rag.service`, resolved with `from app.rag import service as rag_service`. Recorded as ADR-011. Verified: 116/116 tests pass, ruff/black clean, manual `/health` smoke test against a live `uvicorn` process.
3. **Milestone 3 — Done (2026-08-11).** `search_knowledge_base` LangChain tool (`app/tools/knowledge.py`), following the same thin-adapter pattern as Milestone 2's tools: an explicit Pydantic `args_schema` (`question`, optional `game`) and a `make_search_knowledge_base_tool(rag_service)` factory binding an already-constructed `RAGService` (no global singleton). Delegates entirely to `RAGService.answer(question, game)` — no RAG logic duplicated, no `use_hybrid`/`use_multi_query`/`use_compression` exposed to the LLM (retrieval strategy stays an operator/API concern, same status as in `AskRequest`). Returns `{"answer": str, "sources": list[str]}`, mirroring `RagAnswer`/`AskResponse`, so a future agent can surface source URLs without a second call. Not yet wired into an agent or `/assistant` — that's Milestone 5. Verified: 120/120 tests pass (4 new, using a `FakeRAGService` test double per the existing tool-test convention), ruff/black clean.
4. **Milestone 4 — Done (2026-08-11).** Hand-rolled tool-calling loop (`scripts/run_tool_loop.py`'s `run(llm, tools, question, *, max_iterations=5) -> list[BaseMessage]`), not an `AgentExecutor` or any agent abstraction — that's Milestone 5. Binds all four existing tools (`get_player`/`get_team`/`get_match`/`search_knowledge_base`) and drives `LLM → tool call(s) → execution → ToolMessage → LLM` to a final answer, returning the full message history rather than just the answer text. Handles multiple tool calls in one round (the LLM's `AIMessage.tool_calls` can contain several entries; the existing per-call loop covers it with no extra logic) and surfaces tool errors (`app.services.exceptions.EsportsDataError`, the shared base of `PlayerNotFoundError`/`TeamNotFoundError`/`MatchNotFoundError`) as a `ToolMessage` instead of crashing. A `main()` REPL wires real services + a real `ChatOpenAI` for manual demoing, matching `scripts/run_retriever.py`'s existing (untested) interactive-script convention. Tested with `FakeMessagesListChatModel` — no real LLM needed; required a small `FakeToolCallingChatModel` test double overriding `bind_tools` (the stock fake raises `NotImplementedError` since it doesn't implement that method — discovered during planning, not a design change). This loop is deliberately throwaway: Milestone 5's Agent reimplements the same mechanic via library code, not by importing this script. Verified: 124/124 tests pass (4 new), ruff/black clean.
5. **Milestone 5 — Done (2026-08-11).** `app/agents/esports_agent.py`'s `make_esports_agent(llm, tools) -> AgentExecutor`, using `langchain_classic.agents.create_tool_calling_agent` + `AgentExecutor` — first real content in `app/agents/` (empty until now per ADR-011). A `_tolerant()` wrapper, scoped to this module only, converts `EsportsDataError` into a `ToolException` so `handle_tool_error=True` can catch it — confirmed by direct testing that `AgentExecutor` otherwise lets arbitrary tool exceptions crash the run; `app/tools/{player,team,match,knowledge}.py` are unchanged, and `tool.invoke()` called directly still raises the raw domain exception exactly as Milestone 2/3 built it. New `POST /assistant` endpoint (`AssistantRequest`/`AssistantResponse` in `app/api/schemas.py`, `get_agent` dependency mirroring `get_rag_service`'s exact pattern) sits alongside the unchanged `POST /ask`, per roadmap §11's "`/ask` → direct RAG, `/assistant` → Agent + tools + RAG" comparison. `AssistantResponse` mirrors `AskResponse`'s `{answer, sources}` shape; `sources` is aggregated from `search_knowledge_base` calls found in `return_intermediate_steps`. An optional `game` is folded into the agent's natural-language input rather than forced onto every tool call — the LLM decides whether/where to use it. `max_execution_time=60.0` is the basic tool-timeout handling roadmap §12 calls for; `max_iterations` stays at `AgentExecutor`'s default (15). One test-double gotcha discovered while writing the endpoint tests: `search_knowledge_base` calls the shared `llm` internally too (via the RAG chain, Milestone 1), so a sequential fake chat model's `responses` list is consumed by both the agent's own reasoning calls and the RAG chain's call, in interleaved order — not a production bug, just something the fake test double's response list had to account for. Verified: 130/130 tests pass (6 new), ruff/black clean.
6. **Milestone 6 — Done (2026-08-11).** `app/workflows/{state,nodes,graph}.py`: typed `InvestigationState` (§15's suggested shape plus one deliberate addition, `team_name`, needed for `get_match` to have something to look up), six single-responsibility nodes (`analyze_question`, `get_match`, `get_match_data`, `retrieve_knowledge`, `analyze_evidence`, `generate_report`), and `build_investigation_graph(llm, match_service, rag_service)` via `langgraph.graph.StateGraph` — first real content in `app/workflows/` (empty until now per ADR-011). New additive `MatchService.get_latest_match_for_team(game, team_name)` (`get_match`/`find_match` unchanged) — needed because the roadmap's own example question ("why did NAVI lose their latest match") has no `match_id` to look up directly. ## Established conventions for continuing this work

(Full rules live in `.claude/rules/` and the global `CLAUDE.md` — this is just a pointer, not a restatement.)

- One TDD stage = one design spec (via brainstorming) → one implementation plan (via writing-plans) → inline execution → its own feature branch. **Updated 2026-08-09**: branches now fork directly off `master` (the old "off the previous stage's branch" chain was collapsed by merging everything to `master`) — merge back to `master` when a stage is verified, rather than defaulting to "keep as-is."
- Every external dependency (Liquipedia, OpenAI, Qdrant) is injected via an interface (`Source`, `Embeddings`, `BaseChatModel`, `QdrantClient`) specifically so the test suite never hits real network or costs real money.
- Never run `git commit` without printing the message first and getting the user's explicit go-ahead on that exact message.
- **Verify LangChain import paths/behavior by direct testing before writing them into a spec or plan — don't trust docs or memory.** This bit repeatedly during the last three features: `EnsembleRetriever`/`MultiQueryRetriever`/`ContextualCompressionRetriever` all turned out to live in `langchain_classic`, not `langchain_core` or the full `langchain` meta-package (which pulls in `langgraph`, a non-goal); `rank_bm25` is a lazy, undeclared dependency of `langchain_community`'s `BM25Retriever`; BM25's IDF formula degenerates to zero on corpora smaller than ~3 documents; `LLMListwiseRerank` silently passes a capability check but then fails at runtime against this project's fake chat model. Always run a throwaway `python -c` prototype against the real installed library before locking a test or design into a plan.
